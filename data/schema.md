# NYAYA data schema (source of truth)

All data is **synthetic** (generated by `data/generate.py`, fixed seed) except the OpenFEMA declarations used
for the severity mapping (`data/openfema.py`). Amounts are ₹. Feature code lives in `data/features.py` and is
used by both the generator and the API, so offline and online values match.

Files are gzip CSV (`pandas.read_csv("nyaya_v1.csv.gz")`). The IBM image has no pyarrow, so no parquet.

## Payments — `nyaya_<tag>.csv.gz` (one row per payment, sorted by `ts`)

| Column | Type | Meaning |
|---|---|---|
| `tx_id` | str | `T` + 8 digits, in time order |
| `ts` | float | epoch seconds. `T0` = 2026-10-15 12:00 IST (start of the cyclone preset) |
| `hour` | int 0–23 | hour of day, IST |
| `sender_id`, `recipient_id` | str | account ids (see accounts) |
| `type` | str | `PAYMENT` `TRANSFER` `CASH_OUT` (PaySim types) |
| `amount` | float | ₹ |
| `oldbalanceOrg`, `newbalanceOrig`, `oldbalanceDest`, `newbalanceDest` | float | PaySim-style balances, simulated with a running ledger. Unrecorded top-ups happen when a sender runs short (as in PaySim) |
| `geo_shift_km` | float | distance from the sender's usual location |
| `new_device` | 0/1 | device not seen before for this sender (borrowed phone, new SIM, takeover) |
| `merchant_category` | str | `p2p grocery pharmacy clinic fuel telecom electronics jewellery travel utilities cash_out donation` |
| `in_disaster_zone` | 0/1 | payment located in the declared disaster zone during the event |
| `severity_tier` | int 0–5 | zone severity at that hour (0 outside a zone) |
| `device_id`, `subnet` | str | sender device used / sender network (`/24`) |
| `population` | str | **label, never a feature**: `normal` `ato` `displaced` `syndicate` `syndicate_forward` `ngo_payout` |
| `variant` | str | `base` `smurf` `device_spoof` `slow_drip` (red-team syndicate behaviour) |
| `is_fraud` | 0/1 | **label**: `ato`, `syndicate`, `syndicate_forward` |
| `is_mule_recipient` | 0/1 | **label**: recipient is a mule or cash-out account |
| `sender_income_band` | str | `low` `mid` `high` for people; empty for merchants/NGOs/mules. **Fairness audit only, never a model input** |
| Model B features (below) | | recipient features at the moment of this payment (point-in-time, no look-ahead) |

`syndicate_forward` rows are mules passing money on to cash-out accounts. Keep them in the stream (they drive
`forward_within_10m_ratio`); the 10k evaluation suite counts `syndicate` rows as the syndicate payments.

### Populations
- **normal** — residents and others paying merchants (78%), family (18%), and NGO donations during the disaster (4%). Daytime-heavy, known device, small geo shift. Zone residents get `in_disaster_zone = 1` during the event.
- **ato** (1.5% of normal) — account takeover: drains 90–100% of the balance to a fresh account, 86% new device, ~400 km shift, night-weighted, 15% spoof the disaster zone during the event.
- **displaced** — victims paying from camps: essentials (grocery, pharmacy, fuel, clinic up to ₹40,000, telecom, family), 55% borrowed phones, ~60 km shift, night-weighted, crowded relief-camp merchants. **Benign but anomalous — the case legacy engines freeze.**
- **syndicate** — rings of 5 mules + 2 cash-out accounts. Compromised zone accounts are drained to the mules in a 10-minute burst (20–30 per mule), with the zone spoofed. Mules share 2 phones and one subnet, are 1–45 days old, and forward each payment within 1–8 min.
- **ngo_payout** — NGOs collect donations and pay suppliers every 30 min: a benign pass-through account (hard negative for Model B).

### Red-team variants (`--variant`)
| Variant | Change | Expected to weaken |
|---|---|---|
| `smurf` | 3× more mules per ring, ⅓ the payments each | `fan_in_15m`, `unique_senders_15m` |
| `device_spoof` | every mule has its own phone and subnet; senders show a known device 90% of the time | `device_reuse_density`, `shared_subnet_count`, `new_device` |
| `slow_drip` | forwarding delayed 12–40 min | `forward_within_10m_ratio` |

## Accounts — `accounts_<tag>.csv.gz`

`account_id, kind, account_age_days, device_id, subnet, in_zone, displaced, income_band, merchant_category, ring_id, is_mule`

Id prefixes: `P` person · `M` merchant · `N` NGO · `U` mule · `K` cash-out · `A` takeover destination.

## Recipients — `recipients_<tag>.csv.gz`

`tx_id, ts, recipient_id` + the 7 Model B features + `is_mule_recipient, population, variant`. One row per payment
(the recipient's state at that moment). Train Model B on these rows.

## Model A features (`data.features.MODEL_A_FEATURES`)

Model A may use any subset; list the ones used in `artifacts/model_a_meta.json`. Never use labels, ids or income band.

| Feature | Definition |
|---|---|
| `type_code` | PAYMENT 0, TRANSFER 1, CASH_OUT 2, DEBIT 3, CASH_IN 4 |
| `amount`, 4 balance columns, `hour`, `geo_shift_km`, `new_device`, `in_disaster_zone`, `severity_tier` | as above |
| `is_night` | hour ≥ 22 or < 6 |
| `merchant_code` | index in the category list above |
| `orig_balance_err` | `oldbalanceOrg − amount − newbalanceOrig` |
| `dest_balance_err` | `oldbalanceDest + amount − newbalanceDest` |
| `amount_to_balance` | `amount / (oldbalanceOrg + 1)` |
| `orig_drained` | `newbalanceOrig ≤ 1 and oldbalanceOrg > 0` |

`in_disaster_zone` and `severity_tier` are the **disaster context**. The legacy baseline is the same model scored
with both set to 0.

Use `data.features.tx_features_frame(df)` to build the matrix.

## Model B features (`data.features.MODEL_B_FEATURES`, this order)

| Feature | Definition |
|---|---|
| `fan_in_15m` | payments received by the recipient in the last 15 min, including this one |
| `unique_senders_15m` | distinct senders among them |
| `forward_within_10m_ratio` | share of those payments that the recipient has already passed on (sent any payment within 10 min after receiving it), using only payments seen so far |
| `account_age_days` | recipient account age (0 if unknown) |
| `device_reuse_density` | number of *other* accounts registered on the recipient's device |
| `shared_subnet_count` | number of *other* accounts on the recipient's `/24` subnet |
| `mci` | Mule Centrality Index, below |

### MCI (Mule Centrality Index)

Recomputed every 5 minutes of event time over the transfer graph of the last 60 minutes (edge weight = ₹):
`mci(r) = pagerank_percentile(r) × (0.5 + 0.5 × pass_through(r))` for accounts with in-degree ≥ 2, else 0, where
`pass_through(r) = min(1, ₹ sent by r / ₹ received by r)`. PageRank runs on the **undirected** weighted graph
(directed PageRank rewards sinks like shops; undirected PageRank measures centrality within a ring). A payment sees the latest snapshot taken before it.
Online, the API's MCI worker runs the same `compute_mci` on the same windows.
